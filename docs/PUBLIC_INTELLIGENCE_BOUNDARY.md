# Open intelligence, protected execution

Esheen Labs can share powerful, reusable **methods** without exposing domain-specific advantages, customer information or execution authority. The public collection is a set of educational examples with invented inputs and deterministic tests.

## Methods we can share

| Public, reusable intelligence primitive | What it demonstrates |
| --- | --- |
| Competing hypotheses and falsifiers | Do not prematurely select a solution; identify what would disprove it |
| Evidence and provenance receipts | Separate reported claims, tested results and missing evidence |
| Deterministic validation and guardrails | Reject malformed, conflicting or unsafe state changes |
| Independent negative tests | Show what fails, not only the successful demonstration |
| Recoverable task IDs and review states | Prevent duplicate work and document inconclusive outcomes |
| Responsive and accessible-minded interaction patterns | Test real focus, errors, keyboard paths and mobile layouts |

These are *generic ideas* implemented only with original and fictional examples. Code being public does not grant authorization to invoke private runtimes or finance systems.

## What stays private

Private customer/employer source and datasets; private architecture and control-plane instructions; wallet/exchange connections; live positions, financial holdings or transaction records; strategy selection, alpha thresholds and optimization logic; proprietary model outputs and research weights; identity, credentials, keys and signed grants; infrastructure inventory and nonpublic incidents.

We will not publish softened copies of sensitive traces, private Git history, proprietary screenshots, client flows, private financial assumptions or a hidden API endpoint disguised as a harmless demo.

## Safe release boundary

1. Work on generic public components in an isolated, original source root with fabricated data.
2. Review source rights, license compatibility, history and dependency provenance.
3. Enforce an explicit allowlist of files and verify no unrelated files leave the private environment.
4. Run positive, negative, accessibility-oriented and exact-head CI checks.
5. Review public README, issue templates, screenshots, metadata and CI logs for private content.
6. Record public source, tested SHA, deployed artifact and observed live behavior independently.
7. Treat contributors' issue/PR text and model responses as untrusted. A signed, project-scoped executor must be independently enrolled before using Cortex for build actions.

The public Cortex-oriented examples teach observation, challenge and evidence. They do **not** expose private Cortex's database, signed Commander execution interface or autonomous trading engine. No public donation or contribution grants execution permission.
